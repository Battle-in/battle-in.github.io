Практическая работа: проектирование базы данных

Спроектируйте схему данных по техническому заданию ниже. Готовая ER-модель и описание таблиц — результат работы, а не подсказка на странице.

📄 Техническое задание

Проект: информационная система «Кадровый хаб» Назначение: учебный прототип сервиса по поиску работы (аналог hh.ru) Целевая СУБД: SQLite (логическая модель + опционально DDL)
1. Цель разработки

Обеспечить хранение данных о пользователях, профилях соискателей, компаниях, вакансиях, навыках и откликах так, чтобы поддерживались связи между сущностями, целостность данных и возможность типовых выборок (вакансии компании, отклики на вакансию, навыки вакансии и т.д.).

2. Роли (логические, без отдельной авторизации в ТЗ)
  • Соискатель — зарегистрированный пользователь с профилем; может откликаться на вакансии.
  • Работодатель — представитель компании; в рамках ТЗ достаточно хранить компанию и её вакансии (учётная запись работодателя можно не детализировать).
3. Функциональные требования к данным
FR-1 Учётная запись пользователя. Система хранит пользователя с уникальным email, хэшем/полем пароля (достаточно текстового поля password_hash в учебной работе) и датой регистрации.
FR-2 Профиль соискателя. Пользователь может иметь профиль соискателя: желаемая зарплата, стаж (лет), ссылка на портфолио. У одного пользователя не более одного профиля; профиль не может существовать без пользователя. ожидаемая связь 1:1
FR-3 Компания. Хранятся название, сайт, сфера деятельности. Компания может публиковать множество вакансий.
FR-4 Вакансия. Принадлежит ровно одной компании. Хранятся название должности, описание, вилка зарплаты (мин/макс или одно поле — на усмотрение проектировщика), дата публикации, признак активности (опубликована / снята). ожидаемая связь N:1 к компании
FR-5 Справочник навыков. Навык задаётся названием (например, «Python», «SQL»). Одно и то же название навыка не дублируется. Вакансия может требовать несколько навыков; один навык может встречаться во многих вакансиях. ожидаемая связь N:M
FR-6 Отклик. Соискатель (через свой профиль/пользователя) откликается на вакансию. Один соискатель не может дважды откликнуться на одну и ту же вакансию. Для отклика фиксируются дата создания и статус: «рассматривается», «отказ», «интервью». ожидаемая связь N:M с атрибутами связи
4. Ограничения целостности
  • У каждой таблицы — первичный ключ (PRIMARY KEY).
  • Связи реализуются через внешние ключи (FOREIGN KEY) там, где это уместно для SQLite.
  • Email пользователя — уникален (UNIQUE).
  • Название навыка — уникально.
  • Пара «соискатель + вакансия» в откликах — уникальна (один отклик на вакансию от одного соискателя).
  • Обязательные поля помечаются NOT NULL по смыслу ТЗ.
5. Требования к результату проектирования (со стороны заказчика)
  • Схема должна быть приведена к разумной нормализации (минимум 1NF и 2NF; устранение избыточности справочников).
  • Связи N:M не хранятся массивами в одном поле — только отдельными таблицами связи.
  • Допускается краткое текстовое обоснование выбора таблиц (5–10 предложений).
6. Вне scope (не требуется в этой работе)
  • Чат, уведомления, платежи, модерация контента, полнотекстовый поиск.
  • Роли администратора и разграничение прав на уровне БД.

🎯 Задание студента

На основе только разделов ТЗ выше спроектируйте реляционную базу данных для «Кадрового хаба».

  1. Выделить сущности и кратко описать назначение каждой таблицы (1–2 предложения).
  2. Построить ER-диаграмму (от руки, draw.io, dbdiagram.io или аналог): сущности, связи, кардинальность (1:1, N:1, N:M).
  3. Логическая схема: для каждой таблицы — имя, список полей, типы данных SQLite, PK, FK, UNIQUE/NOT NULL где нужно по ТЗ.
  4. Связи N:M — указать промежуточные таблицы; атрибуты отклика (дата, статус) разместить согласно FR-6.
  5. Нормализация: указать, какие аномалии устранены (пример: дублирование названия компании в каждой вакансии).
  6. (По желанию) SQL: CREATE TABLE для двух наиболее показательных таблиц (например, отклик и связь вакансия–навык).

💡 Теги 1:1 / N:1 / N:M в ТЗ — ориентир для самопроверки, а не готовый список таблиц. Имена таблиц и полей вы выбираете сами (единый стиль: snake_case рекомендуется).
